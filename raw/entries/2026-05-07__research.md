# Research: Smithers orchestrator alpha-relevant facts for custom-harness

## Summary
Public Smithers docs and published package source are available. For alpha, Smithers already owns most orchestration behavior: workflow discovery, graph rendering, scheduling, max concurrency, durable SQLite state, resume, approvals, run inspection, and event/log surfaces. Custom-harness can likely simplify to a thin integration around Smithers workflow-pack files and CLI/API invocation rather than re-implementing run semantics.

## Findings
1. **Workflow pack layout is already defined by Smithers.** `bunx smthrs init` scaffolds `.smithers/` with `.smithers/workflows/`, `.smithers/prompts/`, `.smithers/components/`, `.smithers/package.json`, `tsconfig.json`, `bunfig.toml`, `preload.ts`, `agents.ts`, `smithers.config.ts`, `tickets/`, `executions/`, and `.gitignore`; docs explicitly say most teams should start with this pack instead of assembling structure manually. [Installation](https://smithers.sh/installation)

2. **Published source confirms the pack is generated, not convention-only.** The workflow-pack source writes the `.smithers` directories/files and seeded workflows; it also preserves `.smithers/executions` across re-init and seeds package scripts such as `workflow:list` / `workflow:run`. [workflow-pack source](https://cdn.jsdelivr.net/npm/smthrs@latest/src/cli/workflow-pack.ts)

3. **Workflow discovery IDs are filename-derived.** The CLI discovers only `.tsx` files directly under `.smithers/workflows/`, sorts them, and sets `id` to the filename without `.tsx`; display/source metadata comes from `// smithers-display-name:` and `// smithers-source:` comments. `workflow.create` enforces lowercase kebab-case IDs. [workflow discovery source](https://cdn.jsdelivr.net/npm/@smthrs/cli@latest/src/workflows.js)

4. **CLI already exposes workflow discovery commands.** The documented command catalog includes `workflow.list`, `workflow.run <name>`, `workflow.path <name>`, `workflow.create <name>`, and `workflow.doctor`; `workflow.run` runs a discovered workflow by ID with `--prompt`, `--input`, `--detach`, `--run-id`, `--resume`, `--serve`, `--port`, and `--hot`. [CLI reference](https://smithers.sh/cli/overview)

5. **`workflow run` is a wrapper over `up`.** Source shows `workflow run <id>` resolves the discovered workflow and delegates to the same `executeUpCommand` path as `up`; `--prompt` is normalized to `input.prompt` when `--input` is absent, and root defaults to `.` for discovered workflows. [CLI source](https://cdn.jsdelivr.net/npm/@smthrs/cli@latest/src/index.js)

6. **Graph/render is non-executing by design.** `renderFrame` returns a `GraphSnapshot` with `frameNo`, `tasks`, and `xml`, and docs state it “doesn’t execute or persist”; CLI equivalent is `bunx smthrs graph workflow.tsx --input ...`. [renderFrame](https://smithers.sh/runtime/render-frame)

7. **`graph` can render against persisted run context.** CLI docs list `graph <workflow>` as “Render a workflow tree without executing” with `--run-id` and `--input`; source shows it loads persisted input/outputs for the run ID unless input is overridden, then calls `renderFrame` and outputs a JSON-serializable snapshot. [CLI reference](https://smithers.sh/cli/overview), [CLI source](https://cdn.jsdelivr.net/npm/@smthrs/cli@latest/src/index.js)

8. **Run behavior is already durable/resumable.** `runWorkflow` returns `runId`, status, output/error; resume is `runId` plus `resume: true`, loads state from SQLite, skips completed tasks, abandons stale in-progress attempts older than 15 minutes, and requires workflow hash/VCS revision compatibility. [runWorkflow](https://smithers.sh/runtime/run-workflow)

9. **Execution scheduling is Smithers-owned.** The runtime renders JSX to a graph, extracts task descriptors, computes ready tasks based on dependencies/sequence/branch/maxConcurrency, executes, persists outputs to SQLite, and re-renders. [How It Works](https://smithers.sh/how-it-works)

10. **Approvals/human gates are Smithers-owned.** Smithers supports `needsApproval`, `<Approval>`, `approve`, `deny`, `why`, `ps --status waiting-approval`, and resume after approval; denial policies include `fail`, `continue`, and `skip`. [How It Works](https://smithers.sh/how-it-works), [CLI Quickstart](https://smithers.sh/cli/quickstart)

11. **Public types expose stable integration shapes.** `GraphSnapshot` contains `runId`, `frameNo`, `xml`, and `tasks`; `TaskDescriptor` includes node ID, dependencies, schemas, approval flags, retries, timeout, agent, etc.; `RunOptions` includes `runId`, `input`, `maxConcurrency`, `resume`, `rootDir`, `logDir`, `allowNetwork`, `hot`, and progress callbacks. [Types](https://smithers.sh/reference/types)

12. **Current public package is versioned and CLI binary is `smithers` inside `smthrs`.** The latest npm package metadata observed is `smthrs` `0.18.0`, exporting the facade and depending on packages including CLI, engine, db, graph, scheduler, server, time-travel, etc. Docs warn to invoke with `bunx smthrs`, not bare `bunx smithers`, because `smithers` is a different package name. [package metadata](https://cdn.jsdelivr.net/npm/smthrs@latest/package.json), [Installation](https://smithers.sh/installation)

## Concise implications for simplifying the alpha plan
- Treat `.smithers/` as Smithers-owned workflow-pack structure; avoid custom pack layout or custom discovery rules.
- Use workflow IDs as Smithers does: lowercase kebab-case `.smithers/workflows/<id>.tsx` filenames.
- Use `workflow list/path/run` for discovered workflows and `up <file>` for explicit files; no separate custom run dispatcher is needed for alpha.
- Use `graph` / `renderFrame` for previews; do not execute agents or mutate harness state during graph rendering.
- Do not implement custom scheduling, max-concurrency, resume, approval, event/log, or SQLite persistence semantics unless alpha needs a wrapper UI/API; Smithers already owns those behaviors.
- Keep only harness-level constraints: version pinning/invocation (`bunx smthrs`), task-ID stability guidance, input validation, and passing through Smithers status/errors.

## Confidence
High for workflow pack layout, discovery IDs, graph behavior, run/resume behavior, and Smithers ownership of orchestration semantics because the evidence comes from official docs plus published package source. Medium for mapping to “the plan’s proposed constraints” because the exact alpha plan text was not provided in this task; the conclusion applies to constraints about orchestration behavior, not harness boundary decisions.
